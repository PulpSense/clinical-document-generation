# Safe storage retention and sequential admission

The owner-elected policy is **preserve the previous installation during replacement, then source-only recovery after all active/callback gates pass**. This is not a clinical acceptance waiver or promotion/certification change.

## Public maintenance boundaries

`scripts/storage_retention.py` provides explicit, owned-path retirement with exact size/hash/inode/mode inventories, durable per-entry intent and completion, directory fsync and interrupted-deletion reconciliation. It rejects protected-root overlaps, aliases, unknown entries, changed inventories and unavailable owned-process proof. Cooperating installers use the same directory flock. This is not a hostile/noncooperating-writer sandbox: there remains a final syscall race window; stopped workers, owner permissions and cooperative mutation are prerequisites.

`cleanup_completed_workers` accepts only explicit private worker `bin`/`skills` copies and retained counterparts. `completed_operation_cleanup` discovers duplicates only within the operation, retains a canonical original and deduplicates byte-identical `models_dev_cache.json` catalogs. Different catalogs stay intact. Actual model identities, sessions/DB/WAL, usage, stdout/stderr, provenance, request/response checkpoints, native files, approved sources and page images remain. No worker provisioning, permission boundary or shared-profile symlink is changed.

The callback additionally calls `cleanup_stopped_observer_assets` after each finished observer wave. An integer terminal returncode, exited PID/start-tick identity, exact request/provenance hashes, preserved session state and absence of owned live argv/environment/cwd/FD references are required. Canonical assets are stable across later waves. This keeps transient bootstrap copies bounded by one canonical retained original plus the existing three active observer profiles. If safe cleanup fails, another visual worker wave is not allocated: authenticated partial judgments remain, without inventing a pass or marking storage failure as renderer poisoning.

`retire_duplicate_archive` decompresses and CRC-checks bounded ZIPs, rejects unsafe/duplicate/link members and requires every ordinary member's exact size/SHA against retained files. An archive-only `diagnostic-inventory.json` is preserved byte-for-byte beside the durable deletion record. Other only-copy members block deletion. An explicit `strip_prefix='clinical-document-generation'` supports old package ZIPs verified against their still-retained prior tree.

## Governed external installation

The independently reviewed activation-helper-v2 must remain immutable. A separate v3 helper is required to understand `intentionally_retiring` and `retired` journals. It retains the original prior inventory and adds identity/recovery/deletion records; it never treats intentionally missing backups as corruption or attempts local rollback after retirement. New activation reconciles the previous retired transaction before replacing the active tree. Before retirement, the reviewed replacement entrypoint requires committed package/provision/staged/active/host/preservation/backup gates, genuine exact-installed callback/fallback admission, live-origin source reachability and exact prior-tree preservation. The provisional active tree remains rollback-capable until the callback gate passes; callback failure restores the complete prior tree before any durable commit.

For an older historical backup, supply the *current* admitted activation journal separately. Optional obsolete archive paths must duplicate that historical prior tree. Completed `prior-verification-<uuid>`/`backup-verification-<uuid>` trees are eligible only if their entire inventory and manifest equal the preserved prior inventory, with no unique entries. Required process logs and host/render evidence outside those trees are not selected.

Recovery records name exact prior commit/fingerprint and verified origin/branch ancestry. After intentional retirement there is **no local rollback**. Fetch that origin, create a clean detached worktree at the recorded commit (or reconstruct through `git archive`), invoke the ordinary `"$CLINICAL_PYTHON" scripts/workflow.py --package-release <archive>` packager from a committed tree, verify commit/fingerprint, then repeat reviewed installation and actual host/callback admission. A source-only recovery instruction is not an executed recovery.

## Sequential disk admission

`tests/run_tui_acceptance.py --storage-forecast <json>` requires an evidence-hashed, exact-candidate `sequential-storage-forecast/v1` for an owner five-case pilot. Before *every* selected case it samples physical free bytes anew and saves `<planned-operation-id>.disk-admission.json`. Cases supply disjoint retained-growth, worker-peak and scratch allowances plus explained uncertainty. Existing used files are never charged as new allocations. Allocation observations carry complete current inventory/allocated-byte identities; every component maps to selected observation paths, copy count, distinct future population and justification. Missing scope, unsupported totals, changed measurements, double-counted populations and an unjustified margin reject admission. Each owner-pilot invocation launches at most one fresh case and refuses the next case until all preceding exact first outcomes have passing independent native/every-page audits and verified local bytes.

`required_available_bytes` is the **next case** peak. `forecast_sequence_peak_bytes` and `case_peaks` also show projected future retained accumulation, but are not a blanket preallocation gate or guarantee that later cases fit. Actual completed/pending native/page/audit evidence remains on disk and reduces physical free space at the next measurement. Missing/changed observations or insufficient capacity reject before another paid launch. This does not expand the fixed five-family pilot or weaken full-campaign criteria.

The forecast must distinguish observed allocated components from comparable-workload allowances. Do not add old callback totals to a whole-run observation already containing them. The current observed private callback profile is dominated by a roughly 39 MB `bin/tirith` binary, not by copied skills (roughly 4 MB); its roughly 5.6 MB model catalog is also a duplicate cache. Only actual measured accounting and exact duplicate verification support removal. More page units, productive retries, repairs or larger raw logs can exceed a comparable-scope allowance; remeasure, preserve the first outcome and do not silently reuse a stale forecast.
