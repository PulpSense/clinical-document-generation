# AI intake, drafting and independent review (#105)

`prepare` returns the existing obligatory checklist with raw candidate and declared-alias evidence in `intake_review`. The extraction agent consumes it before requesting approval, compares it with preserved input, resolves extraction omissions, and asks one consolidated question for actual obligatory gaps or material source conflicts. Code does not decide whether two clinical representations conflict. The `awaiting_approval` status remains a preparation result, not proof that AI performed this assessment.

Source review returns an explicit `review_delivery.link` and `source_review_reply` with the actual editable-file attachment and approval message. Attach/upload the file through the channel; preserve a clickable accessible link in chat. A host-local path that the user cannot access needs the channel's upload mechanism. This closes the previous path-only payload gap; it does not establish the cause or resolution of a particular live Hermes omission.

Section prompts identify purpose, evidence, ownership and relationships across Protocol, selected ICF and PRS; length goals remain advisory. Applicable template insertion is deterministic. The content reviewer opens actual hash-bound native files, including tables, headers/footers, text boxes and XML values, rather than trusting the construction model. Missing section passages reach review as missing-content anchors. Content and document-scoped page review requests are produced together and use the existing concurrent worker wave. Every rendered page remains individually assessed.

Source-routing obligations remain useful evidence context; a separate fact-by-fact response is no longer mandatory. Normal independent assessments and actual findings carry the judgment. Ordinary style preferences require no repairs or client warning. Finding handoff preserves its complete original response evidence for the general repair integration in #106.

`create_verification_requests(review_context=...)` optionally binds real prior findings and repair-author evidence to fresh requests through the existing ledger/hash. `review_context.prior_findings` carries stable `finding_id`, artifact and targets (raw findings or their `verification_source_finding`). The independent reviewer cites each substantive concern ID in the relevant existing assessment notes with its reassessment, or retains it as a finding. A silent generic pass is incomplete. This is concern continuity, not a per-rule adjudication schema; #106 supplies context and stable IDs for older visual findings that lack them.

Focused tests use controlled reviewer/render adapters, proving source handoff, branch lifecycle, malformed/stale review rejection and concern continuity. Live Hermes judgment, source-file attachment behavior and timing remain owner-run evidence. #107 reconciles the full skill and delivery instructions; #108 reconciles historical tests and prepares that run plan.

## General native repair (#106)

A failed substantive AI assessment creates one `document_repair` request for the complete native document set. The repair author receives approved source/template evidence, stable concern IDs, current native files and retained reviewer evidence. `workspace_path` contains editable deliverable files; `tools_path` holds arbitrary run-local scripts. AI can use DOCX/XML libraries directly for paragraphs, table associations, headers/footers, metadata and arbitrary XML nodes. No edit DSL, rule registry or pre-registered location is required. XML structural diagnostics also use this general workspace rather than the old scalar editor.

The bound `hermes-response/v2` reports `completed`, `disputed` or `needs_review`, actual author/model identity and a summary. Disputes include source-grounded explanations. The workflow verifies request/source/base identities, exact native inventory, file readability and XML structure before adopting a new immutable whole-file checkpoint. Later assembly and renderer font substitution preserve accepted native content. Only objective font replacement operates on those bytes during renderer fallback. Old render/review evidence is invalidated; final package content and every-page visual review operate on fresh actual outputs. Prior substantive findings and all repair-author IDs stay bound to the independent review requests, including exact-envelope transport retries.

Malformed tool/response results receive actionable feedback without clinical findings or adoption. An identical ineffective technical response/workspace after feedback returns `document_repair_no_progress`; an author reporting no productive safe correction returns `document_repair_unresolved`. Both preserve the original candidate for #107's usability/trust assessment and complete review-only delivery. Source/base/integrity mutation remains unavailable. Repeated unchanged substantive actions carry reassessment feedback into the next AI pass; there is no universal repair-count limit. Every pass retains the original operation deadline and asks the author to reserve final verification/delivery time.

Production repair workers receive explicit editing instructions and only workspace/tools writes in the Darwin sandbox profile. The existing Linux `setpriv` launcher does not enforce that profile's filesystem permissions; installed release integrity is checked before and after a repair worker wave, and source/base hashes are verified before adoption on every platform. This preserves the existing Linux runtime contract and detects mutation; it does not claim new Linux filesystem isolation. Installed skill/runtime code is never an authorized repair surface.

Focused public lifecycle tests use actual python-docx/ElementTree editing with controlled reviewers/renderers. They demonstrate native edits, dispute reassessment, newly introduced XML defects, reconstruction preservation, malformed edits, stale responses, source/base mutation and reviewer independence. These adapters establish control flow and byte preservation, not live AI quality or latency.
