# Render Assurance capability resolution

Activation verifies host Microsoft Word or LibreOffice, installs the manifest-bound `pypdfium2` 5.13.0 wheel offline into the release runtime, and verifies approved compatible Liberation fonts. It then verifies package hashes and performs a real DOCX-to-PDF-to-PNG smoke before atomically replacing the active skill. A failed candidate never displaces the previous verified release. Normal document generation remains read-only.

`generate` constructs the complete branch candidate before resolving runtime capabilities. It uses host Microsoft Word or LibreOffice for DOCX-to-PDF rendering; tool failure may advance between those office renderers, while a genuine defect remains bound to the renderer that exposed it. PDF rasterization always uses the one release-owned PDFium runtime. PDFium failure stops Render Assurance with one exact diagnostic and never advances to another PDF backend.

Font probes return available, missing, or unknown. Unknown inventory preserves the requested font and relies on render evidence. Proven missing fonts use the explicit release-owned Liberation mapping; heuristic host substitutions are not accepted. The DOCX bytes, substitution, renderer, page renderer, and every failed attempt are recorded. Capability smoke is not client-ready evidence: final delivery still requires deterministic validation and actual image inspection of every exact rendered page. A genuine defect applies an auditable pagination repair without changing template margins, spacing, fonts, or content, then rerenders on the renderer that exposed it. If the 45-minute ceiling arrives with a genuine unresolved defect, the complete candidate remains internal and the atomic client package remains unpublished.
