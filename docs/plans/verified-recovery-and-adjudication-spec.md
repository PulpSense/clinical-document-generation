# Spec: Verified recovery and adjudication for every blocker

## Problem and outcome

Complete approved studies still stop on small output defects or valid paraphrases. The 2026-10-11 audit identifies shared causes: semantic adjudication is opt-in for selected warning codes; some repair targets lack an executable editing capability; repeated reconstruction can reproduce the same defect; and the function-level inventory does not prove resolution for each emitted condition.

Implement the already-agreed semantic authority of #81 as an enforceable end-to-end contract. For supported, complete, coherent approved inputs, the normal outcome is the complete Client-ready Document Set, with real defects repaired and proven false positives resolved internally. The owner must not need a new code patch for each valid wording variation or generated-document location.

Scope: Prospective/Advarra, Prospective/Sterling, Ambispective/Advarra, Ambispective/Sterling, and Retrospective Protocol-only. Preserve the public intake, approval, generation, recovery and Desktop delivery boundaries. Inspect current implementation before changing it; existing source-bound editing, localization, independent decisions and review bindings are foundations to extend.

This spec follows #81 and complements its outstanding varied-input and Linux evidence work (#89, #90). The rule inventory and executable acceptance requirements below sharpen earlier family-level requirements. No prior evidence obligation is considered satisfied merely by publishing this spec.

## Confirmed decisions

- Stalled content repair switches strategy to independent adjudication within the existing Desktop Operation Deadline. The adjudicator sees approved source, exact current output, failed rule and prior attempts.
- Recovery may edit generated paragraphs, tables, headers and XML structure beyond registered scalar fields, preserving approved facts and required template/legal text.
- Real repairs require relevant checks, rerendering where applicable and fresh independent review of the final candidate.
- Proven false positives and harmless editorial differences do not cause routine delivery warnings or review-only status.
- A genuine unresolved substantive defect at the deadline yields a complete, clearly distinguished Review-only Document Set when usable, source-trustworthy, hash-verified files exist. Explanations remain outside clinical documents.
- Release readiness requires local coverage for every audited route and live repair/false-positive exercises across all five families plus the varied-input campaign.

## 1. Audit closure and rule authority

Replace function-level completeness claims with an inventory of individual emitted conditions. Retain source fingerprints for change detection. Each condition needs a stable rule ID, producer, applicability, authority, evidence inputs, repair capability, adjudication eligibility, verification requirements and behavioral test references. A mixed producer must declare its individual conditions separately.

Classify by what the check proves, not its function name or existing severity:

| Authority | Examples | Resolution |
| --- | --- | --- |
| Trust and identity | Approval lineage, artifact hash, review binding, delivery bytes | Objective verification; semantic decisions cannot waive failures |
| Objective output contract | XML validity, required document set, explicit required exact legal text, demonstrably wrong approved scalar mapping | Source-preserving repair followed by objective recheck |
| Semantic or presentation evidence | Paraphrase coverage, inferred contradiction, word-count proxy, phrase-based unsupported claim, contextual readability | Independent evidence-backed adjudication; repair when confirmed defective |
| Transport or execution | Invalid reviewer schema, failed render, unusable localization | Cause-specific technical recovery, then actual verification |

For numerical, citation and date checks, distinguish identity/relationship obligations from representation heuristics: finding an unmatched numeral alone does not prove clinical information was lost. Exact-copy requirements must cite their authoritative contract. A parser's inferred source contradiction receives source-grounded assessment before requiring user clarification.

Audit all current finding producers, pre-review gates, intake semantic checks, drafting validators, nested/dynamic findings, construction, XML, visual review, reviewer transport and delivery. Use the blocker audit as a starting map, not the completeness oracle. Record migrated rules and remaining gaps by rule ID. Completion requires each existing condition accounted for with a demonstrated executable route.

New or unclassified findings receive an internal technical classification path; they cannot silently become clinical vetoes or be automatically waived. Developer CI must reject unregistered production findings. At runtime, classify their evidence and preserve trust guards; a genuinely unclassifiable condition is an explicit verification limitation, not a fabricated clinical defect.

## 2. Shared evidence and adjudication contract

Semantic findings enter the shared adjudication route regardless of legacy warning/blocking label or whether a pre-review gate raised them. Eligible findings must reach a review request rather than be trapped before review creation. Initial semantic assessment can avoid unnecessary rewriting; unchanged findings after repair trigger independent escalation rather than the same route again.

Bind each request and response to the approved source revision, generation authority, artifact hashes, rule ID/version, expected obligation, current target and relevant prior attempts. Source evidence must identify approved facts or explicit template authority. A finding alleging omission anchors to the inspected section/node inventory and missing obligation; it does not require quoting nonexistent text. Existing-passage findings use exact quotations and unambiguous native locations.

The adjudicator produces one explicit disposition:

- **Faithful / false positive:** quote or locate supporting current evidence and explain why the rule's concern does not hold. This resolves that semantic finding even when its raw matcher still fails.
- **Confirmed defect:** describe the violated obligation, exact target or missing-content anchor, required source-preserving correction and relevant verification.
- **Source clarification required:** identify actual ambiguity or conflict in approved evidence. Model uncertainty or parser limitations alone are insufficient.
- **Insufficient review evidence:** request missing location, artifact view or valid response; this is technical recovery, not approval.

A bare passing review cannot dismiss a specific finding. A decision cannot erase companion defects or waive objective invariants. The adjudicator is a separate review task from the repair author, supplied the source and current candidate rather than instructed to endorse the attempted fix.

Preserve effective resolutions while their bound evidence remains unchanged. Changed evidence invalidates dependent resolutions. Never apply an old decision to a new artifact solely because its error message or rule ID matches. Do not add a parallel publication bypass.

## 3. General source-preserving repair capability

Validate localization and editing capability before dispatch. Missing, ambiguous, duplicated, stale or unusable locations request clarification or a more precise native address. A quotation being present is not sufficient capability proof.

Provide controlled proposals for generated body paragraphs, table cells/rows, headers/footers, metadata and applicable XML nodes/structure, including required insertions and deletions. Use native structural addresses and expected original content/hashes. Proposals describe the edit, approved evidence, affected obligations and protected regions. Derived representations such as formatted names, addresses, dates and units may be constructed from approved facts with an explicit derivation; replacements need not equal one preexisting scalar verbatim.

Validate proposals before accepting them: scope, unchanged source, protected template/legal text, required XML contract and document usability. Protected language may only be restored from its authority or repositioned without changing it. Preserve unaffected content, formatting and relationships. Apply edits to a new candidate, retain history and persist accepted corrections across later reconstruction. Do not self-modify the installed skill during generation.

A failed proposal or invalid post-edit structure returns actionable feedback for a different correction strategy. Rebuilding the same mapper without a changed draft, overlay or construction strategy is not a repair. Reserve enough of the existing deadline for final rendering, review and delivery; do not reset the deadline or silently start another operation.

## 4. Recovery strategy and stopping

For each unresolved finding, track cause, current evidence, attempted strategy, actual target changes and verification results. Judge progress by corrected obligations and candidate differences, not merely distinct model responses.

When repair leaves the same content concern unresolved, escalate to independent adjudication. Distinguish a real remaining defect, matcher false positive, unusable localization, unsupported editing capability, conflicting source and failed reviewer transport. Choose the next capable route from that diagnosis. An unchanged deterministic reconstruction must not immediately establish that the document is clinically defective.

Retain loop protection and the existing deadline. Do not introduce a universal fixed retry count as the product completion policy. Stop nonproductive cycles of the same evidence and strategy, while permitting a materially different capable strategy within the deadline. Repeated malformed responses receive schema-specific recovery; they do not count as repeated clinical defects.

## 5. Verification and delivery

For a real edit, prove the intended change occurred in the native final artifact and preserved source facts. Rerun affected objective checks and applicable structural/integrity checks. Rerender changed DOCX and obtain fresh independent content and every-page visual review of the final required documents. Check the complete Branch Document Set and exact-byte Desktop delivery.

For a false positive, retain the raw failed heuristic and authenticated resolution internally. Final publication uses the resolved semantic disposition, not forced success of that heuristic. Other material concerns, objective invariants and final review requirements still apply. Resolved findings do not become delivery warnings.

Successful delivery contains every required document and no routine warning for corrected defects, harmless alternatives or dismissed false alarms. Review-only delivery contains the complete usable candidate and an external findings notice that identifies unresolved concerns and incomplete assessments. Partial, corrupted or source-untrustworthy packages do not qualify as a complete Review-only Document Set. Preserve previous operations unchanged and distinguish first-operation completion from eventual success after another operation.

## 6. Local acceptance evidence

Use public intake/generation/recovery interfaces and the existing test-pack CLI. Run focused selections only; the full suite still requires explicit approval. Every rule record must link to evidence that actually executes its emitted condition and applicable resolution, rather than merely naming a family test.

Required behavioral coverage:

1. Each semantic rule: faithful variation accepted through adjudication; real omission/contradiction repaired or correctly retained unresolved. Include paraphrases, reordered time expressions, negation, numerical/unit representations and concise complete answers where applicable.
2. Each objective rule: actual corruption remains detectable; repair demonstrably restores the contract; an AI dismissal cannot waive it.
3. Every repair capability: changed final content, approved-fact preservation, persistence through reconstruction and fresh verification. Include tables, headers/footers, generated prose and XML insertion/deletion/derived fields where applicable.
4. Adjudication: unchanged valid bytes can publish despite the raw heuristic; generic passes, unrelated/fabricated evidence and stale source/artifact/rule decisions cannot.
5. Localization: omitted, wrong, duplicate, ambiguous and unregistered passages; missing-content anchors; usable clarification followed by repair.
6. Escalation: ineffective repair, repeated matcher failure, malformed review response, invalid edit, mixed findings and a repair that introduces a new defect. Resolving one finding never clears another.
7. Delivery: complete client-ready package for resolved findings; complete review-only package for genuine unresolved concerns; unavailable outcome for untrustworthy/unusable packages; notices outside clinical text.
8. Audit enforcement: inject an innocuously named semantic blocker, a dynamic finding and a nested/helper producer; CI rejects each until its authority and executable route are covered.

Apply cases across every applicable family: all three Protocol branches, both ICF templates for Prospective/Ambispective, and XML for those active branches. Do not claim ICF/XML coverage from a parameterized Protocol-only test. Objective checks must be tested using actual artifact mutations; simulated reviewers remain clearly identified as controlled evidence.

## 7. Live Linux acceptance and release

Execution owner: the study owner will perform live Hermes verification separately. Live runs are excluded from the approved implementation tickets #92–#102. The implementation must report its local evidence and remaining live-evidence limitations without claiming these runs were completed.

Keep installation verification separate from study generation. Preserve Linux dependency, template, font, renderer and runtime contracts, staged/active DOCX → PDF → page-image smokes and focused installation checks. Ordinary generation does not run maintenance tests.

On the exact release candidate, require:

- One clean baseline, one deliberately introduced real-defect repair exercise and one semantic false-positive exercise in each of the five families. Exercise actual Hermes models, renderer, content review, every-page visual review and exact-byte delivery. Fault injection belongs to a documented test harness, never uncontrolled changes to client source or production artifacts.
- The existing ten-input varied campaign, with independently authored synthetic Brad-style narrative inputs and declared family coverage. Do not tune each input after seeing its output and count that as first-operation success.
- Every operation retained, including failures and automatic re-runs. Record candidate SHA/package identity, source identity, rule/defect injection, strategy, adjudication evidence, final status, delivered hashes, latency and client-visible warnings.
- Separate denominators for ordinary campaign delivery, injected-defect repair, semantic false-positive resolution, review-only outcomes, unavailable outcomes and repeat operations. Local controlled adapters, installation smokes and historical runs do not substitute for this evidence.

All expected-recoverable exercises and the supported complete-input campaign must achieve client-ready delivery within their original operation, without a per-study code patch or concealed extra operation. A failed case must produce a general regression and rerun the affected focused and live coverage on the changed candidate. Unaffected earlier evidence may be reported as historical, not silently attributed to the new release. Do not claim production readiness while required fresh evidence remains missing.

## Implementation sequence and completion

1. Inventory emitted conditions and resolve authority classifications; complete when each existing condition has a rule record and gap/test mapping.
2. Unify adjudication across semantic producers, including pre-review and source-readiness inference; complete when faithful and defective paired cases execute the real routes.
3. Extend native repair capabilities and localization; complete when actual final artifacts demonstrate correction and source/template preservation.
4. Integrate cause-specific escalation, verification and delivery; complete when mixed, stalled and malformed-response lifecycles terminate honestly within the original operation.
5. Enforce coverage in focused CI and update skill instructions; reconcile ADR 0021 and the client-ready delivery language in CONTEXT.md with the confirmed review-only fallback. Preserve unrelated user-owned work.
6. Hand off the implemented candidate for owner-managed live Linux acceptance. Implementation completion and production-readiness evidence must be reported separately.

## Boundaries

This work does not invent missing study facts, silently change approved source, weaken required legal text, waive integrity, remove installation checks or guarantee success during unsupported inputs/provider outages. It does not run the full suite, install a new Hermes version or launch paid certification merely by creating this specification. Existing operator authorization governs those actions. The target is a shared executable recovery architecture with demonstrated coverage, rather than promises of zero future failures.
