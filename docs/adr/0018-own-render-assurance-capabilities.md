# Own the capabilities required for mandatory Render Assurance

Document construction is independent from Render Assurance, while client delivery still requires exact-artifact rendering and page-image review. The client host must provide Microsoft Word or LibreOffice for DOCX-to-PDF rendering. The release owns exactly one PDF-to-image capability: a pinned, manifest-hashed `pypdfium2` wheel installed offline into the release runtime. Package construction derives a deterministic normalized path, byte-length, and SHA-256 inventory from that wheel and binds it to the release fingerprint. Formal installation smoke verifies a pre-promotion candidate only inside the lifecycle-owned installation staging root. An explicitly requested `manual_pre_release` operation may provision and smoke-test a directly extracted, hash-valid unsigned candidate with promotion checks disabled; the operation records that mode and the candidate fingerprint, and it does not confer promotion or certification. Every certified ordinary or active-root assurance requires the independent promotion record, compares its fingerprint with the canonical manifest fingerprint, rehashes its bound installation-assurance bytes, and then rehashes the actual runtime against the immutable inventory. Promotion state is never inferred from deletable assurance or runtime metadata, and writable runtime markers never attest to their own integrity. Native PDFium work runs only in a killable subprocess with governed timeout, page-count, pixel, dimension, output-size, and operating-system resource limits; the parent terminates and reaps the complete process group after timeout, crash, malformed protocol, or successful exit, and failed workers leave no partial page evidence. Linux workers require CPU, address-space, file-size, and open-file limits. Darwin workers require CPU, file-size, and open-file limits but exclude its nonoperational address-space control. A missing mandatory control fails closed. The workflow never discovers alternate PDF backends. A release becomes active only after its host office renderer, PDFium runtime, and compatible fonts pass an end-to-end smoke test, and activation retains the previous verified release atomically.

This supersedes ADR-0009's PDF-backend discovery ladder and revises this ADR's earlier release-owned office-suite decision. We rejected direct GUI screenshot traversal because it is slower and cannot prove deterministic every-page coverage, and rejected downloading a renderer during installation because network and upstream changes weaken reproducibility. The smaller packaged PDFium runtime preserves mandatory Visual QA without redistributing a complete office suite. An incompatible host stops during installation before the first clinical run.
