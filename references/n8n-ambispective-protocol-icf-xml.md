# n8n Ambispective Protocol, ICF, and XML Branch

Use this reference when `meta.study_type` is `Ambispective`.

Read `references/starred-fillout-required-inputs.md` first. Its 35 starred fields are the only ambispective source-input blockers.

## Branch Shape

The existing workflow routes `selectYourTypeOfStudy = Ambispective` through this sequence:

```text
Protocol Type
  -> Introduction1
  -> Population Variables1
  -> Study Design & Methods1
  -> Procedures & Assessments1
  -> Visits Table1
  -> Statistics & Sample Size1
  -> ICF Visits1
  -> Risks & Benefits1
  -> Outcomes1
  -> Build Location Array1
  -> Set Protocol Fields1
  -> Protocol DOCX replacement
  -> XML JSON generation
  -> ICF DOCX replacement
```

The local skill must mimic that sequence:

1. Draft or update `reference/study.reference.json` from the preserved source material.
2. Generate each module output below and save it under `generated.protocol` or `generated.icf`.
3. The public workflow populates the flat n8n variables under `template_fields` through its internal ambispective branch adapter.
4. Generate the named source Markdown, complete the source Markdown approval loop, then render final outputs.

## Ambispective Authoring Rules

- Treat the study as mixed historical plus forward-looking collection. Keep retrospective data sources and prospective visits/follow-up distinct.
- Do not imply that already-collected historical data was prospectively consented unless the reviewed source says so.
- ICF language should describe the participant-facing prospective collection and any review of existing records that the participant is being asked to authorize.
- Protocol methods should state which outcomes come from historical charts/videos and which come from prospective visits or follow-up.
- XML outcome timing should preserve the source of timing, for example `Surgical video review`, `Baseline`, `Month 3`, or `Prospective follow-up`.

| --- | --- |
| `startDate` | Study start date |
| `endDate` | Study end date |
| `lastFollowUpDate` | Last follow-up date |

| `verificationDate` | XML verification date |
| `primaryOutcome` | JSON string for primary outcome array from `Outcomes1.primary_outcome` |
| `secondaryOutcome` | JSON string for secondary outcome array from `Outcomes1.secondary_outcome` |

| `coordinatorFirst`, `coordinatorMiddle`, `coordinatorLast` | Coordinator name parts |
| `locationArray` | JSON string of study locations from `Build Location Array1` |
| `regulatedDrug`, `regulatedDevice` | FDA regulated flags rendered as Yes/No |
| `interventionType`, `interventionName` | Intervention fields |
| `samplingMethod` | Sampling method derived from single-arm vs multi-arm design |

After `scripts/build_prs_xml_fields.py` runs, rebuilt PRS XML templates may use structured row loops under `data_driven_tables.prs_xml` for interventions, arm groups, and primary, secondary, or other outcomes. The legacy indexed fields remain available for the bundled PRS template.

The old n8n `Generate XML JSON1` node used a simplified PRS shape and hardcoded values that the client corrected manually. For final ClinicalTrials.gov PRS XML, do not use that old JSON shape as the output structure. After this n8n mapper runs, run:

```bash
python3 scripts/workflow.py --run-dir <run-dir> --stage generate
```

Use `references/prs-xml.md` for the canonical PRS template, required reviewer-controlled PRS fields, repeated block counts, defaults, and XML validation.

## QA Rules

- Do not expose final ambispective outputs until the public workflow's readiness and delivery gates report no blank required fields.
- `build_prs_xml_fields.py --check` reports all PRS gaps and a `blocking_missing` subset. Ask the reviewer only when `blocking_missing_count` is nonzero; nonstar administration gaps remain visible but nonblocking.
- Do not present final PRS XML as technically valid until `validate_prs_xml.py` passes after rendering.
- Keep missing optional administrative fields blank rather than inventing them.
- Preserve n8n typos such as `sponsortName`, `sponsortAdress`, `ibrName`, `ibrAdress`, `studyCordinatorName`, and `icfStudyLenght&Participants`; copied templates may use those exact names.
- The protocol, ICF, and XML fields must come from the same reviewed `study.reference.json`.
